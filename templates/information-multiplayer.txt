## Goal

Integrate the game with Arcade Academy’s existing multiplayer architecture.

Use Tic-Tac-Toe and Thinking Tanks as implementation references. Preserve the new game’s core mechanics and theme, but align its authentication, lobby flow, questions, Firestore matches, interface, statistics and Hub behaviour.

Do not create a second Firebase implementation.

## Architecture to Preserve

Game
↓
MultiplayerManager
↓
FirebaseManager
↓
Firestore `/matches`

Questions must follow:

Game
↓
MultiplayerQuestionHelper / QuestionManager
↓
Hub-selected class code and question bank

The game must not make direct Firebase Auth or Firestore calls.

## Authentication

The game must reuse the student’s existing Firebase Authentication session.

If the player is not authenticated:

- Do not create an anonymous account
- Do not create another login system
- Show a message directing them back to Arcade Academy to sign in

Use the existing student profile display name in the room.

## Home Screen and Shared UI

Match the Arcade Academy game home-screen conventions.

Include:

- Game title
- Catchphrase
- Description/instructions
- Multiplayer record if tracked
- Create Room
- Join Room
- Five-digit room-code entry
- Question-format selector if the host chooses it
- “Back to Arcade Academy” button
- Creator credit where applicable

Use `shared/css/global.css` and the established panel, button, typography and responsive conventions.

The entire page must be scrollable where required.

Add accessible controls for:

- Leave Room
- Leave Game
- Return to Menu
- Rematch, if supported
- Error and connection status

Leaving must stop Firestore listeners and return the player safely to the game home screen.

## Match Lifecycle

Use the existing `/matches/{roomCode}` architecture.

Support the appropriate states:

- `waiting`
- `lobby`, if players must confirm readiness
- `playing`
- `finished`
- `abandoned`

Room codes must:

- Be five digits
- Be collision-safe
- Permit direct lookup but not collection listing
- Reuse abandoned or stale rooms only through the approved FirebaseManager flow

Store only multiplayer information required for the match. Do not copy full user profiles or educational records into match documents.

## Questions

Use the existing multiplayer question helper and QuestionManager.

If the host selects a question format:

- Save the selected format in match settings
- Validate that it is one of the supported formats
- Ensure both players see the same match rule

If each player uses their own question bank:

- Player A loads questions using Player A’s Hub-selected class code
- Player B loads questions using Player B’s Hub-selected class code
- Do not store one player’s class code as the other player’s source
- Both banks must use the match’s selected question format
- Show a clear error if a player’s bank lacks that format

Apply the question mechanic specified above.

For a before-turn gate:

- The active player receives one question
- Correct answer allows the configured action or bonus
- Incorrect answer applies the configured consequence
- Prevent duplicate answers and repeated submissions
- Store only the gate result required to synchronize the turn
- Do not expose answers in Firestore

Record educational answers locally through PlatformManager and QuestionManager for the student who answered them.

## No Multiplayer Coins or Score Rewards

Multiplayer games must not award or deduct shared coins.

Do not award:

- Coins for answers
- Coins for winning
- Coins for losing
- Coins for draws
- Score-based coin bonuses

Record only the existing multiplayer outcome statistics where supported:

- Games played
- Wins
- Losses
- Draws
- Questions and accuracy
- Playtime
- Last played

If the game has an internal tactical score required for gameplay, keep it match-local and do not turn it into coins or persistent Arcade Academy score rewards.

## PlatformManager

Use:

- `PlatformManager.startSession(gameId)`
- `PlatformManager.endSession(gameId)`
- `PlatformManager.heartbeat(gameId, active)`
- `PlatformManager.recordQuestionAnswered(gameId, correct)`
- Existing multiplayer result recording methods

Do not count waiting in a lobby or answering menus as active gameplay.

Do not start duplicate sessions after rematches.

## Firestore Security Rules

Check the existing `/matches` rules against the exact fields and status transitions used by this game.

Do not weaken the `/users` rules.

The rules should:

- Require authentication
- Allow creation only by Player 1
- Allow Player 2 to join a waiting room
- Restrict updates to match participants
- Preserve core match identity
- Allow only approved mutable fields
- Prevent collection listing
- Prevent client deletion
- Support lobby status if readiness is required
- Include the new game ID in the approved multiplayer game IDs

If deployment is required, update the repository’s rule example and clearly provide the exact block that must be published. Do not claim the rules were deployed unless deployment actually succeeded.

All two-player game artwork panels should use Arcade Academy’s approved dark-blue multiplayer background.

## Firebase and Teacher Dashboard

Keep all direct Firestore operations in FirebaseManager.

Ensure the Teacher Dashboard can read the student’s multiplayer statistics through the existing game catalogue.

Do not sync:

- Match transcripts
- Opponents’ questions
- Correct answers
- Full terrain/board history after the match
- Coins

Persistent match documents may remain for room recovery/auditing only as permitted by the existing architecture.

## Recovery and Edge Cases

Handle:

- Host leaves before another player joins
- Player leaves during the match
- Opponent disconnects
- Page refresh during an active room
- Old room stored in localStorage
- Missing or abandoned room
- Room already full
- Missing class code
- Unsupported question format
- A player’s bank lacking compatible questions
- Duplicate move submission
- Duplicate reward/result claim
- Rematch request from only one player
- Stale room-code reuse
- Firestore permission failure

Errors must be friendly and actionable.
