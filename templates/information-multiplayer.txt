## Goal and Reference

Integrate the game completely with Arcade Academy’s established shared multiplayer architecture. Support:

1. Student versus Student through MultiplayerManager and Firebase `/matches` rooms.
2. Student versus class-calibrated computer when the game supports an AI mode.

Use Thinking Tanks and Tic-Tac-Toe for online structure and Shuriken Scholar for shared home-screen, typography, panels, buttons, shops, and cosmetic-list conventions. Preserve the game’s mechanics and artwork.

This template is for games whose primary competitive experience is already shared-state multiplayer. Do not add Challenge Mode to these games.

## Required Architecture

```text
Game -> MultiplayerManager -> FirebaseManager -> Firestore /matches
Game -> MultiplayerQuestionHelper / QuestionManager -> Hub-selected bank
Game -> PlatformManager / AchievementManager -> FirebaseManager
CPU mode -> shared AI difficulty data -> privacy-safe class statistics
```

- Never call Firebase Auth or Firestore directly from game code.
- Never duplicate Firebase configuration, authentication, questions, coins, achievements, cosmetics, saves, or room management.
- Use UID as identity; display only approved student-facing names.
- Load `gameconfig.js` before PlatformManager.
- Load `../../shared/css/global.css` before local `style.css`.

Inspect the complete game folder plus FirebaseManager, MultiplayerManager, MultiplayerQuestionHelper, QuestionManager, PlatformManager, GameSaveManager, AchievementManager, `global.css`, Thinking Tanks, Tic-Tac-Toe, Shuriken Scholar, Hub catalogue code, Firestore rules, and Teacher Dashboard architecture.

## GameConfig

Expose `window.GAME_CONFIG` and use one stable ID everywhere. Include the established metadata and:

```javascript
gameModes: ["singleplayer", "multiplayer"],
primaryMode: "multiplayer",
challengeMode: { enabled: false, types: {} }
```

Also declare players, min/max players, supported question formats, AI support, high-score support, achievements, and level rewards as appropriate.

The Hub and Teacher Dashboard must discover the game through configuration rather than hard-coded lists.

## Shared Home-Screen Layout

Follow the shared hierarchy:

1. Title and catchphrase
2. Compact relevant statistics and shared coins
3. Shop button when progression/cosmetics exist
4. Description/instructions
5. Mode selection: `Single Player` and `Multiplayer`
6. Mode-specific controls
7. `Back to Arcade Academy`
8. Creator credit

For multiplayer show Create Room, Join Room, five-digit numeric code entry, lobby/readiness state where needed, and visible connection errors. For CPU mode show the current shared difficulty choices and Start control.

- Do not add a Challenge Mode button.
- Return to the game home screen after a completed match.
- Hub link is `../../index.html`.
- Home pages and overlays must scroll correctly on desktop, mobile, and iPad.
- Keep the title, catchphrase, statistic boxes, selectors, mode controls, and action groups aligned to one centred home-screen column at every viewport size.
- Put concise How to Play controls and rules inside the Description/instructions section instead of a separate tab or screen.
- Fill the available viewport without clipping or an unintended inset game window, while preserving board/canvas aspect and input-coordinate accuracy where mechanics require it.
- When a game has enemies, home-screen animation may use only that game’s existing enemy sprite assets or renderer. Never create generic substitutes or borrow enemies from another game.
- Non-enemy backdrop art must come from the game’s own objects and visual language. The backdrop must cover the home screen, remain behind content, ignore pointer input, and have a useful default before the player unlocks anything.

## Global CSS, Fonts, Themes, and Shared Values

Use `shared/css/global.css` as the design source for fonts, colours, panels, buttons, tabs, borders, radii, gradients, glows, success/error feedback, links, and responsive conventions.

Use `--font-title`, `--font-subtitle`, `--font-body`, the shared accent/background variables, gradients, and component classes. Local CSS should supply game artwork and gameplay layout, not an unrelated UI system.

- Multiplayer Hub cards and default multiplayer home backgrounds use the approved dark blue unless an equipped theme overrides UI presentation.
- Themes may change home/menu backgrounds, UI colours, fonts, borders, panels, and question arrangement.
- Themes must never change gameplay rules, physics, hitboxes, turn logic, board state, player/enemy sprites, weapons, or gameplay colours needed to distinguish players.
- Correct feedback follows the active theme’s positive colour; incorrect feedback uses a readable inverse/contrast.
- Shared UI cosmetics apply to the game UI as well as the Hub.
- AchievementManager applies shared state through root `data-arcade-theme`/`data-arcade-cosmetics` attributes. Do not clear or replace them, and do not use permanent page-wide inversion/filter effects.
- Home screens must retain a pointer-free behind-content layer for shared animated theme art, while the actual multiplayer board/canvas remains mechanically and visually unmodified by UI themes.
- Shared badge, border, font, holographic-hover, and Living Level HUD effects should come from shared hooks/classes instead of duplicate per-game implementations.

## Shared Shop and Cosmetics

Follow Shuriken Scholar’s shop structure and linear item presentation:

- Shop opens from the home screen.
- Cosmetics are a tab inside the same shop, never a separate floating design.
- Use shared shop/tab/button/item classes.
- Keep every tab’s contents present when switching; changing tabs must not erase other inventory.
- If no shop exists, create one with an in-layout home Shop button and Cosmetics tab.
- Place the Cosmetics tab/content before the Back/Return control.
- Show only unlocked compatible rewards.
- All normal rewards are toggleable and compatible slots can be combined.
- Secret rewards become always-active after unlock and can coexist.
- Game cosmetics remain in the game shop; Hub/global themes, fonts, badges, borders, and shared effects remain in Hub Upgrades.
- Implement and verify every declared visual effect. Never advertise configuration-only cosmetics.

Gameplay-changing rewards are disabled in human multiplayer. They may affect CPU mode only when explicitly declared, and must not affect ranked/leaderboard eligibility.

## Online Multiplayer

Use `/matches/{roomCode}` only through MultiplayerManager/FirebaseManager.

Support the shared states `waiting`, `lobby`, `playing`, `finished`, and `abandoned`. Room codes are collision-safe five-digit numbers. Permit direct room lookup, not collection listing. Store only required match state—never emails, full profiles, educational histories, or class data.

All clients subscribe to the room snapshot and update automatically after every accepted move. Never require a manual browser refresh between turns.

Validate:

- Only authenticated participants can act.
- Turn ownership and move legality are checked transactionally.
- Winner and finish state are deterministic.
- Repeated submissions cannot apply a move twice.
- Leave/abandon and reconnection states are visible.
- Rematches require both players and reset only round state.
- Local UI remains responsive while waiting for Firebase.

Normal multiplayer documents include `expiresAt`. Production cleanup can use a Firestore TTL policy for collection group `matches`, field `expiresAt`. Abandoned matches expire sooner; active updates extend the expiry. TTL setup is deployment infrastructure, not game logic.

## Authentication and Privacy

Reuse the Hub’s Firebase Authentication session. Do not create anonymous accounts or another sign-in screen. If signed out, send the player back to the Hub with a clear message.

Use Firebase UID as database identity. Never rely on display name as identity and never expose opponent UID, email, class history, or answers in player-facing data.

## Questions

Use MultiplayerQuestionHelper and QuestionManager.

- Each student uses their own Hub-selected class and question bank.
- Never synchronize question order, exact answers, or one player’s bank to the opponent.
- Synchronize only the shared match rule/format and game outcome data needed for the match.
- When the host chooses a format, store and validate the format in match settings.
- Record each student’s answers through PlatformManager.
- Show clear missing-class, unsupported-format, unavailable-bank, loading, and older-room compatibility errors.
- Question overlays pause local active-play accounting where appropriate.

## CPU / Class-Calibrated AI

When CPU mode is supported, use the shared AI difficulty architecture and privacy-safe class aggregates. Provide the established difficulty choices. Do not fetch named student records or create game-specific teacher-data queries.

CPU mode uses local game state and must not create a `/matches` room. Clearly distinguish CPU and human results in emitted achievement/statistic events.

## Platform Statistics, Coins, and Saves

Use PlatformManager for sessions, active playtime, questions, result statistics, coins, and shared events. Use GameSaveManager/the approved local pattern for game-only progression. Never create a second currency or overwrite unrelated game data.

Exclude menus, lobbies, shops, questions, pause states, connection waits, and result screens from active playtime.

Do not award normal question coins twice when a game also has a match reward. Human multiplayer economy rules must be explicit and transaction-safe. Practice/test matches grant no permanent rewards.

Teacher resets must clear only the intended statistics and progression.

## Achievements, Levels, and Effects

Use AchievementManager and stable data-only events. Add at least:

- One educational human/CPU performance achievement
- One distinctive game-mastery achievement

Each requires a globally unique ID, name, description, tier, scope, and declarative conditions. Include result, CPU/human mode, difficulty, question totals/accuracy, comeback/close-match state, and game-specific summary where relevant—never opponent personal data.

Regular achievement tiers award XP only. Cosmetics and small CPU-only boosts come from level rewards or Secret achievements. Configure approximately four cosmetics to one small gameplay reward and implement every effect.

- Practice/test matches cannot unlock achievements or advance XP.
- Prevent repeat-opponent farming through shared policy.
- Human multiplayer ignores all gameplay-changing boosts.
- Visual cosmetics may apply only when they do not obscure board state, player identity, aiming, or accessibility.

## Hub and Teacher Dashboard

Categorize the game primarily as Multiplayer even when CPU mode exists. Use the approved multiplayer-blue card/background unless changed by a UI theme. Display available shared statistics through the normal card structure.

Teacher Dashboard reads the shared catalogue and PlatformManager/Firebase data. Do not add direct game-specific Firestore queries.

## Verification

Test with two different authenticated accounts and verify:

1. GameConfig loads and Hub categorization is Multiplayer.
2. `global.css`, shared fonts, home layout, buttons, panels, shops, and themes match conventions.
3. There is no Challenge Mode UI or ChallengeManager initialization.
4. CPU mode starts without creating a Firebase room.
5. Create/join uses a five-digit code and both clients enter the same room.
6. Both clients update after every move without manual refresh.
7. Illegal/out-of-turn/duplicate moves are rejected safely.
8. Each player receives questions from their own class bank.
9. Disconnect, leave, finish, draw, win/loss, reward claim, and rematch work.
10. Shop tabs retain their content; cosmetics form a linear unlocked-only list and effects toggle correctly.
11. Gameplay boosts do not affect human multiplayer.
12. Shared statistics, active playtime, achievements, resets, and Teacher Dashboard values work.
13. `expiresAt` is present on newly created/updated match documents.
14. Desktop, mobile, touch, and iPad layouts remain usable.
15. JavaScript syntax, page-load, repository formatting, and Firestore-rule checks pass.

Report files changed, architecture used, match states and question formats, CPU behaviour, achievement/cosmetic effects, shared versus local data, tests performed, assumptions, and any Firestore rule, TTL, billing, or deployment requirement.

Ask only when a missing decision materially changes gameplay, privacy, or economy. Otherwise follow current shared conventions and the named reference games.
