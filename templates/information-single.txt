## Goal and Reference

Integrate the game completely with Arcade Academy while preserving its core gameplay and visual identity. Use Shuriken Scholar as the primary reference for home-screen structure, shared styling, shop tabs, linear cosmetic lists, achievements, questions, platform statistics, and Challenge Mode. Inspect another mechanically similar aligned game before editing.

Implement and verify the integration. Do not merely write a review.

## Required Architecture

Keep these boundaries:

```text
Game -> QuestionManager / PlatformManager / AchievementManager / ChallengeManager
Shared managers -> FirebaseManager
FirebaseManager -> Firestore
```

- Never import Firebase or call Firestore directly from a game.
- Never create a second coin, class-code, question, achievement, cosmetic, authentication, or save system.
- Keep game mechanics local. Shared managers observe and record them.
- Load `gameconfig.js` before `PlatformManager.js`.
- Load `../../shared/css/global.css` before the game’s own `style.css`.
- Use the current cache-version convention on shared scripts.

Before editing, inspect the full game folder plus:

- `games/shuriken-scholar/`
- `shared/css/global.css`
- `shared/js/PlatformManager.js`
- `shared/js/FirebaseManager.js`
- `shared/js/QuestionManager.js`
- `shared/js/GameSaveManager.js`
- `shared/js/AchievementManager.js`
- `shared/js/ChallengeManager.js`
- `shared/data/classes.js`
- `question-banks/banks.json`
- `app.js` and the Hub catalogue/configuration path

## GameConfig Is the Source of Truth

Create or correct `gameconfig.js` and expose it as `window.GAME_CONFIG`.

Use one stable game ID for the Hub, PlatformManager, Firebase statistics, saves, achievements, Challenge Mode, Teacher Dashboard, favourites, and cosmetics. Include the established fields where relevant:

- `id`, `title`, `name`, `icon`, `catchphrase`, `description`, `genre`, `entry`
- `gameModes: ["singleplayer", "challenge"]` when Challenge Mode is enabled
- `primaryMode: "singleplayer"`
- `players`, `questionType`, `supportedQuestionFormats`
- `requiresQuestionBank`, `supportsHighScores`, `supportsAchievements`, `createdBy`
- `achievements`, `levelRewards`, and `challengeMode`

Do not hard-code catalogue metadata elsewhere when GameConfig can provide it.

## Shared Home-Screen Layout

Match the established Shuriken Scholar hierarchy while retaining game-specific artwork:

1. Game title and catchphrase
2. Compact lifetime/relevant statistics and shared coin balance
3. Shop button, if the game has progression or cosmetics
4. Short description and instructions
5. Question-bank/class status
6. Main Start button
7. Shared Practice button
8. Shared Challenge Mode button directly beneath Practice
9. `Back to Arcade Academy`
10. Creator credit where appropriate

Requirements:

- The Hub link must navigate to `../../index.html`.
- The home screen must scroll at small desktop and touch widths.
- Do not manually create Practice or Challenge buttons. PlatformManager and ChallengeManager insert them beside the configured Start button.
- Add `startSelector` to GameConfig only when the standard selectors cannot find the normal Start control.
- Returning from game over, a run summary, or the shop must refresh displayed coins and statistics.
- The main game-over continuation is `Return Home`, not an automatic restart.

## Global CSS, Fonts, Themes, and Shared Values

Use `shared/css/global.css` for all shared presentation values:

- `--font-title`, `--font-subtitle`, `--font-body`
- `--bg-primary`, panel colours, accent colours, success/error colours, and `--gold`
- `--gradient-panel`, `--gradient-btn`, hover/active gradients
- shared border widths, radii, glows, panels, buttons, tabs, shop items, and links

Use the shared classes (`panel`, `btn`/`canva-button`, shop/tab classes, and game-home link conventions) before adding game-specific CSS. Game CSS may define artwork and gameplay layout, but must not replace the global design system with unrelated fonts, button geometry, modal structure, or hard-coded shared colours.

Theme behaviour:

- Hub themes may change home/menu backgrounds, UI colours, borders, fonts, panels, question arrangement, and non-gameplay background art.
- Themes must not alter gameplay rules, collisions, physics, questions, game objects, player/enemy sprites, projectiles, or gameplay readability.
- Home-screen and behind-game backgrounds may use theme variables where a background exists.
- Correct-answer feedback uses the active theme’s appropriate positive colour; incorrect feedback uses its readable inverse/contrasting colour.
- UI effects must work on game home screens and game UI, not only on the Hub.
- AchievementManager applies shared state through `data-arcade-theme`, `data-arcade-cosmetics`, and related root attributes. Do not remove, overwrite, or permanently cache those attributes/classes.
- Do not apply page-wide `filter`, hue rotation, inversion, or forced canvas recolouring for a UI theme. Shared themes must remain reversible when disabled.
- Leave a safe behind-content layer on home screens for shared animated theme art such as Storybook words; it must be pointer-free and must not enter the gameplay update/collision loop.
- Shared UI effects such as Academy Badge, Living Level Badge, holographic hover cards, themed borders, and fonts must use shared hooks/classes rather than game-specific duplicate implementations.

## Shared Shop and Cosmetic Layout

Follow Shuriken Scholar’s shop conventions:

- Open the shop from the home screen.
- Use one shop modal/window rather than a separate floating cosmetics screen.
- Use tabs such as `Upgrades`, `Powerups`, and `Cosmetics` as appropriate.
- Cosmetics are another tab inside the existing shop.
- If no shop exists, create a shop with a home-screen Shop button and a Cosmetics tab.
- Use the shared shop classes and a single-column/linear item list.
- Put the Cosmetics tab above the shop’s Back/Return control.
- Cosmetic buttons must match the size, font, border, colour, and interaction style of other shop buttons.

AchievementManager owns the shared cosmetic inventory and injects/renders the game’s cosmetic rewards. The game provides the compatible shop host and implements the actual visual/gameplay effect.

- Show only rewards the player has unlocked.
- Every non-secret cosmetic/boost must be toggleable.
- Allow compatible slots to be equipped together (for example border + background + character).
- Equipping one item replaces only an incompatible item in the same slot.
- Secret rewards are always active once unlocked and may coexist.
- Game-specific cosmetics stay in that game’s shop; Hub/global themes, fonts, badges, and borders stay in Hub Upgrades.
- Never display an unlock whose effect has not actually been implemented.

## Achievements, Level Rewards, and Effects

Use the shared AchievementManager. Never create per-game achievement persistence.

GameConfig must contain at least two original achievements:

- One educational/performance or improvement achievement
- One achievement for mastery of the game’s distinctive mechanic

Each achievement needs a globally unique stable ID, name, description, tier, scope, and declarative requirement. Bronze/Silver/Gold/Platinum achievements award XP only. Regular achievements do not contain direct cosmetic rewards. Cosmetics and small boosts come from level rewards or Secret achievements.

Register a stable `levelRewards` pool with approximately four cosmetics to one small gameplay reward. For every reward:

- Declare a stable ID, name, type, slot, game ID, and accurate player-facing detail.
- Implement and verify the effect; configuration alone is insufficient.
- Apply sprite/outfit colours consistently to all relevant player variants.
- Apply trails/exhaust/projectile effects to the actual emitted effects.
- Keep gameplay boosts small, single-player-only, and excluded from Practice and human multiplayer.
- Report stable, data-only events through PlatformManager/AchievementManager for mechanics that cannot be derived from shared statistics.

Practice mode must not advance achievements, XP, levels, coins, high scores, cosmetic progression, secrets, or permanent progression.

## Questions

Use QuestionManager and the class selected on the Hub.

- Never fetch a question bank directly from Firebase.
- Never create a second class-code selector.
- Validate supported formats and normalize through the shared question architecture.
- Record every answer through `PlatformManager.recordQuestionAnswered(gameId, correct)`.
- Pause active gameplay time while a question overlay is open.
- Provide clear loading, empty, incompatible-format, missing-class, and bank-load error states.
- Do not expose answers or one student’s question sequence to another system.

Suggested messages:

- `Please enter your class code on the Arcade Academy Hub.`
- `This class does not have compatible questions for this game.`

## PlatformManager, Coins, Statistics, and Saves

Use the real shared API after inspecting its current implementation:

- `startSession`, `endSession`, and `heartbeat`
- `recordQuestionAnswered`
- `setHighScore`
- `getCoins`, `addCoins`, and the approved deduction/spend method
- stable game-specific event reporting where required

Active playtime excludes home, pause, shop, question, loading, and game-over screens. Use the shared coin balance and never allow a deduction below zero.

Apply the supplied correct reward and incorrect penalty. If either is `NOT DECIDED`, ask rather than inventing an economy value.

Use GameSaveManager or the approved existing local-save pattern for game-only upgrades, inventory, skill trees, and permanent abilities. Use PlatformManager/FirebaseManager for shared statistics and currency. Preserve old save keys and migrate changed save shapes safely.

Teacher reset requests must clear the appropriate statistics/progression without accidentally deleting unrelated coins, unlocks, or other games.

## Challenge Mode

Challenge Mode is for games that are fundamentally single-player. It runs two completely independent local runs toward a shared objective. It never synchronizes enemies, movement, physics, health, weapons, upgrades, drops, question order, random events, or game state.

Declare compatibility only in GameConfig:

```javascript
challengeMode: {
  enabled: true,
  types: {
    scoreAttack: { enabled: true },
    survival: { enabled: true },
    distanceRace: { enabled: false },
    waveRace: { enabled: true },
    timeAttack: { enabled: true, targetScore: 15000 },
    questionRace: { enabled: true, targetCorrect: 25 },
    accuracyChallenge: { enabled: true, minimumQuestions: 20, durationSeconds: 300 }
  }
}
```

- Enable only metrics the game genuinely exposes.
- Register a small adapter with ChallengeManager when the standard Start button or metric snapshot is insufficient.
- Report meaningful changes through `ChallengeManager.update(...)`; call `finish(...)` once at the natural run end.
- Do not write every animation frame. The shared manager throttles updates, but the game should still report meaningful state changes.
- Preserve all player upgrades, loadouts, saves, and independent randomness.
- Wagers and rewards remain owned by PlatformManager/FirebaseManager.
- Wager controls support `0`, direct entry, `-10`, `-1`, `+1`, `+10`, and `MAX`; Ready locks the wager. A loss deducts the player’s wager, a win adds `Math.floor(wager * 0.5)`, and a draw changes no coins.
- The shared opponent HUD reports only the selected objective’s metrics. Never upload local game state.
- Question Race defaults to 25 correct; Accuracy defaults to 20 qualifying answers/300 seconds unless GameConfig overrides them; Time Attack always needs a game-specific target.
- The global kill switch is `CHALLENGE_MODE_ENABLED` in `shared/js/ChallengeManager.js`.
- Do not add Challenge Mode to games whose established multiplayer mode is already their primary competitive experience.

Challenge documents use `/challenges/{roomCode}` and include `expiresAt`. Production cleanup may use a Firestore TTL policy on collection group `challenges`, field `expiresAt`.

## Hub and Teacher Dashboard

The Hub must discover the game from GameConfig and place it in Single Player. Its card uses the standard dark single-player artwork and displays supported shared statistics without a hard-coded game list.

Teacher Dashboard data must flow through the shared catalogue and managers. Do not add direct per-game Firestore reads. Support high score, questions, correct/incorrect, accuracy, playtime, last played, sessions, and applicable game metrics.

## Verification

Verify at minimum:

1. GameConfig loads before PlatformManager and the game appears in the correct Hub section.
2. `global.css` loads before local CSS and shared fonts/variables are used.
3. Home-screen order, responsive scrolling, Shop, Practice, Challenge, and Hub link match the conventions above.
4. Shop tabs remain present when switching tabs; cosmetic items are a linear list and only unlocked items appear.
5. Every configured cosmetic/boost visibly or mechanically works, toggles correctly, and combines by compatible slots.
6. Themes affect UI/home backgrounds without changing gameplay objects or mechanics.
7. Class selection and every supported question format load correctly.
8. Correct/incorrect answers, coins, high score, sessions, and active playtime reach PlatformManager.
9. Game over returns home and refreshes displayed values.
10. Practice gives no permanent rewards.
11. Challenge create/join, wager adjustment, ready, shared challenge selection, independent runs, HUD, result, rematch, and forfeit work with two accounts.
12. Challenge progress is throttled and no local game state is uploaded.
13. Teacher resets and dashboard values work.
14. Desktop, touch, and iPad gestures do not zoom or hide controls unintentionally.
15. JavaScript syntax, page-load checks, and repository formatting checks pass.

Report files changed, shared integrations completed, challenge types enabled, achievement/reward effects implemented, question formats, economy values, local versus cloud data, tests performed, assumptions, and any required Firestore rule/TTL/deployment step.
